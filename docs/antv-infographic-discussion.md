# AntV Infographic 採用に関する検討メモ

> 2026-09-27 の検討セッションの整理。目的は「インフォグラフィック作成」ではなく
> 「柔軟なオプションをもつテキストの画像化」であり、AntV Infographic
> (`@antv/infographic`) がその目的に耐えうるかを評価した議論の記録。

## 1. 背景と採用した構成

- 既存の satori カードパイプラインは維持し、infographic は新フォーマットとして共存
  （PR #7 で `DocumentRenderer` 実装の `infographic` レンダラとしてマージ済み）。
- 本文は分割せず 1 ブロックのまま DSL に流し込む。MVP はテキストのみのシンプルな
  テンプレート。外部リソース依存を持たないため CSP 変更不要。
- PNG 出力はライブラリ側の `toDataURL({type:'png'})` を使い、satori 側と
  SVG→PNG の共通ラスタライズロジックを共有しない。
- AI による自由文→DSL 生成は対象外。

## 2. フォント管理のアーキテクチャ

フォント管理はアプリ側が握っており、ライブラリ任せではない。

- `satoriEngine.ts` がフォント取得の単一経路: jsDelivr から TTF を fetch →
  Cache API → `FontFace` で `document.fonts` へ登録 → satori へはバイナリ提供。
- infographic 側はライブラリ同梱の CDN フォント 5 種を `registerFont` で無効化し、
  DSL theme にファミリ名を明示 + 描画前に `loadSatoriFonts()` で登録 +
  エクスポート時に同一バイナリを埋め込み。同一バイナリ・同一ファミリ名で
  ライブラリとの整合を取っている。
- 将来フォント選択機能を入れる場合も流れは同じ: アプリ側がバイナリ取得・登録し、
  DSL の `font-family` に選択値を流すだけ。ライブラリは「ファミリ名で描画する装置」。

## 3. SVG/PNG エクスポートとフォント埋め込み

- SVG を `<img>` で読むとブラウザは「secure static mode」で処理し、外部リソース
  取得もホストの `document.fonts` 参照もできない（ライブラリ固有ではなくブラウザ
  共通の仕様）。このため PNG ラスタライズ時も SVG 内への data: URI フォント
  埋め込みは必須であり、dom-to-image 等すべての SVG→PNG ライブラリが同じ対応を
  取っている。
- PNG 化時の埋め込みは一過性（メモリ内のシリアライズコピーのみ）。ディスクに残る
  PNG は軽量で、14MB 級のフォント埋め込みが永続するのは SVG ダウンロード時のみ。
  「PNG が基本、SVG はプレビュー/本生成の single source of truth」という運用方針と
  矛盾しない。
- コスト: TTF の fetch+base64 化はセッションで 1 回（キャッシュ済み）、PNG 化ごとの
  シリアライズは数十 ms 程度、ネットワーク転送ゼロ。

## 4. フォント形式対応（woff2 / ttf / otf）

- ブラウザ描画（プレビュー/infographic）は `FontFace` が 3 形式ともネイティブ対応。
  SVG 埋め込みは data: URI の mime を変えるだけ。
- satori は woff2 非対応（ttf/otf/woff のみ）。woff2 を使うには `wawoff2`（WASM）で
  TTF へ一度だけ変換する経路が必要。satori 公式もこの経路を推奨。
- 結論: infographic 限定なら追加ライブラリ不要で 3 形式対応可能。satori カードと
  フォント選択を共用にする場合、woff2 選択は infographic 専用にするか wawoff2
  変換を入れるかの分岐が必要。
- Fontsource 等のパッケージは woff2 のみ配布が多い点に注意（satori には使えない）。

## 5. AntV Infographic の想定リスク

1. **全テキストが `foreignObject`（HTML 埋め込み）描画** — 最大の特性上の注意:
   - 生成 SVG は「真の `<text>` ではない」ため、Illustrator 等の SVG 編集ツールや
     foreignObject 非対応ビューアではテキストが出ない/編集不可。ブラウザ表示・
     PNG 化は問題なし。
   - Safari で `<img>` 内 SVG の foreignObject が描画されない歴史的問題があり、
     PNG エクスポートが空白になる可能性。要実機検証（最もリスクの高い未検証点）。
2. **非公開/若い API への依存** — `viewBox` の型キャスト、`loaded`/`error`
   イベント、`registerFont` による CDN フォント無効化など内部挙動に依存。
   0.2.x で流動的、アップグレード時に壊れ得る（現在 `0.2.20` 固定）。
3. **DOM 計測ベースの環境差** — `measureBlockHeight` が実ブラウザの
   `getBoundingClientRect` に依存。jsdom では動かず（early-throw 対応済み）。
4. **バンドルサイズ** — dynamic import で緩和済みだが初回選択時に大きめのチャンク。
5. **テンプレート追加のたびに CSP/外部リソース確認が必要** — アイコン・イラスト系
   テンプレートは CDN 依存になり得る。

### CDN フォント無効化の安全性

- バージョン固定のため意図しない挙動変化はアップグレード時のみ。
- 仮にライブラリが新しい CDN フォントを追加して fetch を試みても、CSP
  （`font-src 'self'`）がブロックする二重防御。最悪「読み込み失敗ログ」止まり。
- DSL theme で自前スタックを明示しているため、ライブラリのフォントが読めても
  使われない。

## 6. 非決定性の整理

「非決定性」は**環境間のズレ**であり、同一環境・同一データでプレビューと本生成の
ズレではない。

- プレビューも PNG エクスポートも、同じブラウザ内で同じ DSL→同じ DOM 計測→同じ
  SVG を経由する同一パイプラインのため、その環境では一致する。
- 環境間で変わり得るもの:
  - フォント未ロード環境（初回オフライン等）ではフォールバックフォントで計測・描画。
  - ブラウザエンジン間のテキストレイアウト・subpixel 丸めの微差で行折返しが
    1 行ずれる可能性。はみ出し防止は実 DOM 計測→フォント縮小ループで担保して
    いるため、最悪「別ブラウザでフォントが一段小さい」程度で表示崩壊はしない。

## 7. 柔軟性（オプション化）の評価

「柔軟なオプションをもつテキストの画像化」への耐えうる度合い:

- **動的テーマ生成**: 可能。実装済みの `buildInfographicDsl` が DSL の `theme`
  ブロックを毎回動的に生成（`colorBg`/`colorPrimary`/`palette`/`fill`/
  `font-family` を RenderTheme から流し込み）。
- **フォント・文字色・背景色の切り替え**: 名前付きテーマの切替は必須ではない。
  「テーマ」は値の束に過ぎないため、フォント選択・色選択を独立したオプションと
  して `optionFields` に足すだけで実現可能。
- **自動フォント縮小**: 実装済み。`ti-text` カスタムコンポーネントが実 DOM で
  折返し高さを計測し、超過中は 90% 刻みで縮小（下限 45%）。
- **表示しきれない検知**: 実装済み。最小サイズでも収まらない場合は末尾省略し、
  `getWarnings` が警告を返してプレビュー下に表示。
- **任意サイズ指定**: `sizes` 配列への追加だけで任意の W×H（例: 1920×1080）に
  対応可能。自由入力にするなら入力欄追加が必要。
- **短文をパンパンに拡大**: 現状は「はみ出したら縮小」のみ。上限を引き上げる
  小変更で「短い文は枠いっぱいまで拡大」も可能。

## 8. satori メイン化の障壁整理

**実質的な障壁**

1. **woff2 非対応** — フォント選択を woff2 まで広げるなら wawoff2 変換が必要。
   Noto Sans JP 固定の現状では無関係。
2. **フォントバイナリ管理が前提** — グリフを SVG パスに埋め込む方式のため
   バイナリ供給が必須（`satoriEngine.ts` の基盤あり済み）。

**工数が必要なもの（障壁というより自前実装）**

3. テンプレートなし: リスト/ステップ/タイムライン等は全て flexbox+自前計測で書く。
4. テーマ・装飾は全て自前（AntV のプリセット資産に相当するものはない）。
5. プレビューは canvas ラスタライズ経由（SVG→`<img>`→canvas）で一回り迂回。

**satori が優れる点**

6. DOM 非依存・決定論的: 純粋 JS→SVG 文字列。jsdom/Node/将来のサーバー化でも動き
   環境間で出力が一致。
7. 出力 SVG が真のベクタ（グリフはパス埋め込み）: foreignObject の Safari 問題・
   SVG 編集ツール非対応が無関係。`<img>` ラスタライズでフォント埋め込み不要。

**satori で対応できない/弱いもの（テキスト画像化の範囲で）**

- **縦書き**: `writing-mode` 非対応。疑似実装は可能だがルビ・約物処理は困難。
  **日本語縦書きカードが欲しい場合の最大の制約**。AntV は foreignObject 内 HTML
  のため縦書き可能 — ここは逆転ポイント。
- **絵文字**: フォントにグリフがないと出ない。twemoji 差込み機構はあるが追加実装
  とアセット管理が必要。
- **文字装飾**: テキスト縁取り・文字グラデーションは非対応。背景グラデーションや
  影は可。
- CSS サブセット制約: grid/absolute の複雑レイアウト、transform 回転の一部等は
  限定的。
- **自動フォント調整・任意サイズ・パンパン調整**: いずれも可能。
  `layout.ts` の `fitFontSize`（折返し計測+二分探索）が既に動作中。最小サイズ
  でも収まらない場合の検知は warnings 機構の流用で数行の変更。任意サイズは
  `satori(element, {width, height})` が直接受ける。短文拡大は探索上限を引き上げる
  だけ。

## 9. 結論（現時点の評価）

- 「柔軟なテキスト画像化」が目的なら、妨げは実質 woff2 対応と縦書きのみ。
  両方不要なら satori メイン化に本質的な障壁はない。
- AntV Infographic が報われるのは将来リスト/ステップ/タイムライン等の構造
  テンプレートや縦書き出力が欲しくなった時。第二フォーマットとして残すのが
  合理的。

## 10. 残検討事項（未着手）

  wawoff2）。
- 任意サイズ指定 UI / 短文時の grow-to-fill フォントサイズ。
- フォントバイナリの自己ホスト化（runtime CDN 依存の排除、初回オフライン耐性）。
- `satoriEngine.ts` から `src/lib/render/fonts.ts` へのフォント層分離リファクタ。
- Safari 実機での foreignObject PNG エクスポート検証。
